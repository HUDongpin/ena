# Nova worker and execution boundary

Nova uses the real Qwen/DeepSeek chat-completion tool protocol to write TypeScript files. The Next.js process only authorizes/enqueues runs, reads durable events/artifacts and renders validated declarative output. A separate worker runs `scripts/nova-worker.ts`; generated code executes exclusively in a gVisor (`runsc`) or Kata container. No host `eval`, `vm`, local-import fallback or generated dependency install is provided.

## Dedicated worker setup

Use a dedicated Linux x64 host with Docker and a working `runsc` runtime (or explicitly configured `kata-runtime`). The worker has access to the Nova PostgreSQL store and its encryption configuration, plus the selected provider credentials. Keep that host separate from the web application and research/data workspaces. Only per-job synthetic files are mounted into the container. The Docker CLI receives a minimal environment; no provider keys, database URLs, SMTP credentials or user data enter the container.

1. Install this repository's locked dependencies with `npm ci` on that host. This supplies the pinned `esbuild` 0.28.2 package and Linux x64 binary used by the trusted compiler.
2. Resolve and verify an immutable official `node:24.15.0-bookworm-slim@sha256:<digest>` image for the worker platform. Set it as `ENA_NOVA_NODE_IMAGE` and run `node scripts/nova-sandbox/build.mjs`. The build script copies only the trusted harness, pinned esbuild files and Dockerfile into a temporary context; application configuration and research files are excluded. It prints an immutable `sha256:<image-id>` value.
3. Set `ENA_NOVA_SANDBOX_IMAGE` to that exact image ID. A registry reference with `@sha256:<digest>` is also supported after it is pulled onto the worker. Set `ENA_NOVA_SANDBOX_RUNTIME=runsc` (the default). There is no `runc` fallback. The image is never pulled during a user run.
4. Apply the Nova database migration and configure the existing Plugin Lab database/encryption settings. Set `ENA_NOVA_ENABLED=true` for the web application and worker, and `ENA_NOVA_WORKER_ENABLED=true` only for the worker. The web application needs the same sandbox image/runtime configuration for the static readiness gate; this does not grant it Docker access.
5. Set the Nova provider variables on the worker: `ENA_NOVA_QWEN_API_KEY` / `ENA_NOVA_QWEN_BASE_URL` and/or `ENA_NOVA_DEEPSEEK_API_KEY` / `ENA_NOVA_DEEPSEEK_BASE_URL`. The existing `OPEN_ENA_QWEN_API_KEY` and `DEEPSEEK_API_KEY` are supported fallbacks. Only official HTTPS provider bases are accepted. Nova never substitutes a different selected model or provider.
6. Run `node --import tsx scripts/nova-worker.ts` under the host's service manager. `--once` handles at most one claimed run and one notification batch for operational checks. SIGTERM/SIGINT aborts active provider/container work and leaves its checkpoint recoverable after the lease expires.

The worker drains the expert email outbox every 30 seconds using the existing configured SMTP transport. It reports fixed error messages without recipient or credential details. The authenticated `/api/nova/notifications/deliver` endpoint can also be scheduled independently; leases prevent duplicate simultaneous delivery.

## Sandbox limits and evidence

Each container has no network, a read-only root and read-only synthetic job mount, non-root UID/GID 65532, all capabilities dropped, `no-new-privileges`, 32 PIDs, 1 CPU, 256 MiB RAM/no swap expansion, a 32 MiB temporary filesystem, a 25-second container deadline and bounded child/host output. Host cancellation terminates the Docker command and removes the named container. Generated TypeScript and generated test code run in separate child processes, each with a restricted `vm.SourceTextModule` realm inside the mandatory container. No host objects/process/require are supplied, dynamic code generation is disabled, and tests receive an in-realm assertion shim. `buildPlugin(context)` is synchronous: Promise and thenable results are rejected. A trusted wrapper captures the realm serializer before module evaluation, invokes the exported function and serializes the result within the realm timeout. Only a serialized primitive string crosses back; realm-produced objects and thenables never reach host `await` or JSON serialization. Unpredictable completion receipts are required after the exported function and test assertions complete. The VM is defense in depth, not a substitute for the OS sandbox. Compiler bundles remain in the trusted supervisor's memory, so the plugin cannot replace the test bundle on disk.

The host revalidates the JSON output and immutable synthetic analysis values regardless of what the generated process reports. Source paths and manifest fields are allowlisted. Node identity, both group edge sets and their weights, group labels and table values must remain unchanged. Presentation coordinates, labels, colors and row/edge order may change. Generated tests add useful assertions but are not treated as independent scientific validation.

Provider thinking parameters are sent on the wire. Qwen receives `enable_thinking` and its configured `thinking_budget`; DeepSeek receives `thinking.type=enabled` and `reasoning_effort`. The 32,768 `max_tokens` output limit is independent of Qwen's thinking budget; DeepSeek includes thinking in its token limit. Budget values are upper bounds, not evidence that the model spends those tokens. Requests use SSE, preserve `reasoning_content` privately for tool continuation, cap request/response bytes, reject redirects and redact all provider error bodies. Durable client events report actual tool completion without exposing reasoning.

Runs stop at the selected effort's provider-step and repair limits, or a 30-minute worker wall limit. Leases are checked before each provider/tool call and polled during active work. Each checkpoint contains the exact files, provider messages and counters. A worker restart resumes unresolved tool calls; explicit user continuation starts a new bounded attempt. Completion requires matching source hashes and passing trusted checks on the current files. Artifacts remain private drafts with source/fixture hashes and no production activation.

## Validation limits

`tests/nova-provider.test.ts` uses injected HTTP responses to verify protocol, bounds, cancellation and redaction without paid provider calls. The sandbox tests use explicitly labeled injected synthetic container results to test the host trust boundary. These tests do not prove the selected regional model is available or a secure container ran on this machine. Run `ENA_NOVA_TEST_SECURE_SANDBOX=true node --import tsx --test tests/nova-sandbox-live.test.ts` with the immutable image and secure runtime configured. It includes a valid TypeScript draft plus stdout/exit, constructor-escape, dynamic-import, hostile thenable/Promise, getter-timeout and assertion-failure probes. These probes are skipped when the secure container is unavailable. A separately authorized bounded live provider check is also needed before enabling a deployed worker. If Docker, the immutable image or the secure runtime is unavailable, Nova reports a blocker; it never executes generated code on the host.

The pre-provider scope gate conservatively recognizes common English and Chinese inference requests (including t-tests, p-values, regression and significance tests) and pauses for expert review. This text check does not prove recognition of every possible intent; the output schema and immutable-value checks enforce the actual scientific boundary. Descriptive text is never evidence of scientific approval.
